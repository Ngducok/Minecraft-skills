# Mechanics before genres

| Mode family | Core decisions | Relevant domains |
| --- | --- | --- |
| Survival/hardcore | Native simulation, death/recovery, renewability | Simulation, items, world content |
| Creative/building | Edit ownership, undo, templates | Building, claims, schematics |
| Adventure/puzzle | Objective evidence, traversal, save/reset | Objectives, maps, movement |
| PvP/PvE | Damage rules, attribution, teams, encounters | Combat, entities, sessions |
| Minigames/party | Entry, rounds, winner/draw, temporary state | Sessions, menus, teams |
| Parkour/racing | Movement bounds, checkpoints, timing | Movement, sessions, maps |
| Technical/automation | Native compatibility, conservation, load | Processing, simulation, performance |
| Roleplay/cooperation | Identity, communication, shared rights | Teams, permissions, localization |
| Resource/economy modes | Supply/rewards, ownership, optional money | Items, objectives, transfers |

Families overlap; this is a routing aid, not an exhaustive list of all custom
games. A new genre can reuse underlying mechanics while requiring its own rule
research. Do not force XP, farming, custom quality, a shop or islands into a mode.

For each feature record entry, action, success, failure, reset and persistence.
Confirm edition/platform support, build the smallest playable loop, then measure
balance and input on representative clients. Imported design patterns remain
hypotheses until tested in this mode/runtime.
